# Project Persistence Boundary

## Purpose

This document defines which parts of the `Project` aggregate are eligible for persistence.

The goal is to maintain a strict separation between:

- runtime project state
- persistent project state
- persistent knowledge generated by analysis

The `Project` aggregate remains the runtime source of truth during execution.

---

# Persistence Model

The persistence architecture follows this boundary:

Project
(runtime state)
        |
        |
        v
ProjectPersistentState
(persistent project configuration)
        |
        |
        v
PersistentProjectKnowledge
(analysis knowledge snapshot)


---

# Persisted Project State

The following `Project` information is eligible for persistence.

## Project Metadata

Persist:

- project identity
- project name
- project root path
- project description
- project version
- creation timestamp
- update timestamp

Reason:

Project metadata defines the identity of the analysed repository and is required to restore project context.

---

## Project Configuration

Persist:

- analysis configuration
- scanner configuration
- ignore rules
- project-specific settings

Reason:

Configuration affects analysis behaviour and must remain consistent between executions.

---

# Analysis Knowledge Persistence

Analysis-generated knowledge is persisted separately through:

PersistentProjectKnowledge


This includes:

- file identities
- symbol identities
- chunk identities
- embedding metadata
- retrieval metadata when applicable

Reason:

These entities represent durable knowledge created by Codelp analysis.

---

# Runtime State

The following `Project` fields must never be persisted directly.

## Parser State

Examples:

- parser objects
- parser execution results
- parser runtime structures

Reason:

Parser output depends on implementation details and can be regenerated.

---

## Index State

Examples:

- in-memory indexes
- index services
- runtime lookup structures

Reason:

Indexes are derived data and must remain rebuildable.

---

## Chunk Runtime State

Examples:

- chunking execution objects
- temporary chunk builders

Reason:

Only stable chunk identities belong to persistent knowledge.

---

## Embedding Runtime State

Examples:

- embedding providers
- model instances
- runtime caches

Reason:

Providers and execution state are environment dependent.

---

## Retrieval State

Examples:

- search results
- active queries
- ranking state

Reason:

Retrieval depends on runtime user interaction.

---

## Context State

Examples:

- generated context windows
- temporary MCP context

Reason:

Context is execution-specific and not durable knowledge.

---

# Persistence Rules

## Rule 1 — No Runtime Dependencies

Persistent models must never contain:

- services
- providers
- runtime objects
- external resources
- circular references

---

## Rule 2 — Deterministic Representation

The same project state must produce the same persistent representation.

Persistence must preserve:

- stable identifiers
- deterministic ordering
- reproducible metadata

---

## Rule 3 — Project Remains Aggregate Root

Persistence must not bypass the `Project` aggregate.

The flow must remain:

Project
    |
    v
Persistent Representation
    |
    v
Storage

Never:

Storage
    |
    v
Project mutation

---

# Future Evolution

Future milestones may extend persistent state with:

- Git metadata
- detected languages
- dependency information
- repository statistics
- analysis history

Any extension must preserve the separation between:

- runtime state
- persistent state
- durable knowledgey
